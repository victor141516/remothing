# HDR: stream an HDR display as HDR, or convert it to SDR well

- Status: under discussion
- Created: 2026-11-11

## Goal

When the streamed display is in HDR mode, what the client gets today is an
automatic conversion to SDR. Instead:

- a client that supports HDR should get the picture in HDR;
- a client that does not should get a better conversion to SDR than
  today's.

Nothing is to be implemented from this file yet: the user asked for
everything to be written down first. It holds what the work consists of,
what was measured (2026-11-11), and the decisions taken so far.

## Open questions

1. **Which half first**: the SDR conversion of our own (server only, every
   client gains, and it fixes a picture that is plainly wrong today) or
   HDR to the clients that can show it? Recommended: SDR first; the HDR
   half builds on its capture.
2. **Video precision.** In the browser tested, a decoded picture reaches
   the page with 8 bits per channel whatever the stream has (see
   "Precision"). Choose:
   - a) HDR video in 8 bits with a curve of our own: most codes for the SDR
     range, the rest for highlights. Works with every codec, H.264
     included. Smooth bright gradients may show bands.
   - b) full 10 bits through a `<video>` element, which the browser shows
     in HDR by itself, but with its own brightness mapping (see "Decoded
     video"). Only fits the motion mode of task 002, where the whole
     picture is video.
   - c) both: a) in tile mode, b) in motion mode.
3. **HDR for the lossless layer too?** It is cheap: 10-bit tiles take the
   same 4 bytes per pixel as today's and reach the screen exactly (see
   "Canvas"). Without it, an area that stops moving would fall back from
   HDR video to an SDR tile. Recommended: yes.
4. **The worker.** The client draws in a worker, and a canvas drawn from a
   worker only shows HDR while the page's own thread shows a small HDR or
   wide-gamut canvas (see "Canvas"). Recommended: keep the worker and add
   a 1-pixel WebGPU canvas in `extended` mode to the page, the one switch
   that also worked with the client's `desynchronized` canvas; a
   display-p3 canvas where there is no WebGPU.
5. **Clients of both kinds on one display**: two versions of the picture
   at once (HDR and SDR), or one for all?
6. **Highlights in the SDR picture**: what is brighter than white has to
   be squeezed. A fixed roll-off, or adjustable?

## Decided (2026-11-11)

By the user:

- For now only documentation. Tickets and implementation come later.
- Other browsers and macOS are assumed to behave like the browser tested
  (Edge on Windows). The client detects what it needs and stays in SDR
  when something is missing; what turns out different gets fixed then.
- Linux: best effort.

By the agent, as the user asked ("take whatever decision"):

- **The picture is always taken relative to the host's SDR white**, read
  from Windows at that moment. That makes the "SDR content brightness"
  setting irrelevant to what the client sees. See "The SDR content
  brightness setting".
- **Linux**: nothing to implement for Linux hosts now, because nothing we
  can capture there is HDR; the new parts are kept behind the platform
  traits so that a Linux capture can join later. See "Linux".

## What happens today

Measured on this PC's HDR display (see "Browser test" for the method),
with the Windows setting "SDR content brightness" at 280 nits:

- Windows capture asks Desktop Duplication for 8-bit BGRA and nothing else:
  `DuplicateOutput1(device, 0, &[DXGI_FORMAT_B8G8R8A8_UNORM])` in
  `duplicate`, `crates/platform-windows/src/dxgi.rs`. Windows then converts
  the HDR desktop itself, and it does it by cutting everything off at
  80 nits:

  | on the desktop | what we receive |
  |---|---|
  | grey 32 | 64 |
  | grey 64 | 117 |
  | grey 96 | 171 |
  | grey 128 | 225 |
  | grey 160, 192, 224, white | 255 |
  | anything brighter than white (HDR) | 255 |
  | pure red, green, blue | unchanged |

  So the stream of an HDR display is not a careful conversion: it is 3.5
  times too bright, and everything from a light grey upwards is white.
  The conversion is not ours and there is nothing in it to tune.
- On systems where only the older `DuplicateOutput` works, an HDR desktop
  is not captured at all: the frame is rejected with "desktop image format
  ... is not BGRA" (same file; read in the code, not tried).
- Everything after capture is 8-bit SDR: the shared screen copy and the
  tile comparison (BGRX), the lossless tiles, the encoder input texture,
  the video stream (marked BT.709, limited range, in
  `crates/encoder/src/ffmpeg.rs`), the client's textures and its canvas.

## The SDR content brightness setting

Windows Settings, Display, HDR: "SDR content brightness". The user asked
how it affects the capture and a conversion to SDR.

What it does (Microsoft's documentation, sources 1 and 2, and the
capture):

- In HDR mode Windows composes the whole desktop in linear light, in a
  16-bit float format where 1.0 means 80 nits (scRGB).
- Programs that draw in HDR write absolute brightness. Ordinary (SDR)
  programs are multiplied by the setting: SDR white is placed at
  `level / 80`. The level is read with `DisplayConfigGetDeviceInfo`
  (`DISPLAYCONFIG_SDR_WHITE_LEVEL`, in thousandths of 80 nits).
- Measured here: the API says 280 nits, and in the float capture SDR white
  reads 3.50 (= 280 / 80), grey 128 reads 0.755, pure red (3.50, 0, 0).

What it does to today's stream:

- Windows' 8-bit conversion ignores the setting: it treats 80 nits as
  white and cuts above it (table in "What happens today"). The higher the
  slider, the more of the picture is washed out. Only with the slider at
  its lowest (80 nits) would today's picture be right. That last sentence
  follows from the numbers; the slider was not moved to try it.

What it does to a capture in float:

- SDR content arrives multiplied by `k = level / 80`, here 3.5. Dividing
  by `k` gives it back exactly: from the float capture, the nine greys
  and three pure colours on the test page all return to their original
  8-bit values.
- An independent write-up (source 3) measured the same on another PC at
  240 nits (a test picture with all 256 levels came back exact) and
  checked the arithmetic for seven levels between 80 and 480 nits.

Decision:

1. Read the level together with the HDR state, per display.
2. The conversion pass works on `capture / k`: 1.0 is the host's SDR
   white, whatever the slider says.
3. **SDR picture**: values up to 1.0 are encoded as sRGB, which is exact
   for everything an SDR program drew. Values above 1.0 (only real HDR
   content) are rolled off towards white keeping the hue, pixel by pixel
   and always the same way; no curve that adapts to the picture, or
   unchanged areas would change between frames.
4. **HDR picture**: the values are sent as they are, in multiples of
   white, and the client shows 1.0 at its own white. The client then sees
   the same proportion between white and highlights as the host's screen.
5. **When the setting changes**: read the level again. Windows documents
   `IDXGIFactory1::IsCurrent` for changes of HDR capabilities; whether it
   reports a slider move is not known, so also ask for the level about
   once a second (one cheap call).
6. Result: moving the slider changes nothing for SDR clients, not even a
   tile. For HDR clients only real HDR content moves, because its
   proportion to white changes on the host too.

Sunshine does not do this: it uses a fixed 300 nits for the cursor because
"there is no API that provides that information to Win32 apps"
(`src/platform/windows/display_vram.cpp:1823-1826`), and its documentation
says an SDR stream from an HDR host is "probably overexposed".

## Browser test

Question: can the browser put HDR on a WebGL canvas, and how does a
decoded picture get there? Done by hand with pages of its own; the client
was not touched.

### Method

- This PC's main display (`\\.\DISPLAY1`, 3840x2160) was already in HDR
  mode: 10 bits, SDR white at 280 nits, peak 465 nits (Windows display
  settings and `IDXGIOutput6::GetDesc1`). The second display, the one the
  demo streams, has HDR off.
- Edge 156 (Chromium), a visible window on that display, default flags
  unless said otherwise. No other browser is installed here.
- The pages draw patches of known brightness. A tool outside the browser
  then reads what reached the screen: it duplicates the display asking for
  the 16-bit float image and averages each patch. Values are linear scRGB,
  1.0 = 80 nits; below they are given in nits. Control patches: SDR white
  reads 280 nits, pure red (3.50, 0, 0), 50 % grey 0.76.
- Nobody had to look at the screen: every number below was measured.
- The canvas rows were measured with one canvas per page and the browser
  restarted for each row. It matters: an earlier round with several
  canvases on a page gave wrong conclusions, because one canvas can switch
  the whole page to HDR.

Scratch files, git-ignored, on this machine only: `.tools/hdr-probe/`.
`src/main.rs` is the tool: `hdr-probe` lists displays with HDR state,
white level and peak; `hdr-probe capture <display> x,y,w,h ...` reads
patches from the float image, `capture8` from the 8-bit image we get
today. `web/` has the pages (`single.html` one canvas, on the page or in
a worker; `index.html` the decoded-video cases; `levels.html` greys and
HDR steps; `precision.html`) and the test pictures. The pictures were
made with FFmpeg (a downloaded build, since removed): one 1280x720 10-bit
frame with five grey bars at 100, 203, 400, 1000 and 4000 nits on the PQ
curve, or a ramp through all 877 luma codes, encoded with libx265
(Main 10) and SVT-AV1, signalled as BT.2020 PQ or as plain sRGB / BT.709.

### Canvas: where HDR appears

Patches at 1, 1.5 and 3 times SDR white, so 280 / 420 / 840 nits is the
right answer.

| canvas | on screen |
|---|---|
| on the page's thread: WebGL2, 8-bit (what the client has) | 280 / 280 / 280 |
| WebGL2 with a float drawing buffer, sRGB | 280 / 280 / 280 |
| WebGL2 float, colour space display-p3 | 280 / 419 / 839 |
| WebGL2 float sRGB, with an 8-bit display-p3 canvas next to it | 280 / 419 / 839 |
| WebGL2 float sRGB, with a WebGPU `extended` canvas next to it | 280 / 419 / 839 |
| WebGPU, `rgba16float`, tone mapping `extended` | 280 / 419 / 839 |
| WebGL2 opaque (`alpha: false`, as the client asks), float asked | 280 / 280 / 280: the float buffer is refused (`INVALID_OPERATION`) |
| in a worker (OffscreenCanvas), alone: WebGL2 float, sRGB or display-p3 | 280 / 280 / 280 |
| in a worker, alone: WebGPU `extended` | 280 / 280 / 280 |
| worker WebGL2 float + a float sRGB canvas on the page | 280 / 280 / 280 |
| worker WebGL2 float + a display-p3 canvas on the page (8-bit or float; 8 px or 1 px) | 280 / 419 / 839 |
| the same, that canvas outside the window, `visibility: hidden` or `opacity: 0` | 280 / 280 / 280 |
| worker WebGL2 float or WebGPU + a 4 px WebGPU `extended` canvas on the page | 280 / 419 / 839 |
| worker WebGL2 float with `desynchronized: true` asked: alone, or with the display-p3 canvas | 80 / 95 / 129: the values go out as raw scRGB (1.0 = 80 nits) |
| worker WebGL2 float, `desynchronized` asked + the WebGPU `extended` canvas | 280 / 419 / 839 |
| 10-bit tiles: an `RGB10_A2` texture with PQ codes and our curve in the shader, in that last setup | 138 / 280 / 554 / 1377 / 5494 (wanted 138 / 280 / 552 / 1379 / 5517) |

- A float drawing buffer is `gl.getExtension('EXT_color_buffer_float')`
  and then `gl.drawingBufferStorage(gl.RGBA16F, width, height)`. Values
  are sRGB-encoded with 1.0 = SDR white and go on above 1.
- The float buffer alone is not enough. Values above white only appear
  while the browser composes the page in HDR, and what switches a page is
  something drawn by the page's own thread and visible: a WebGPU canvas
  in `extended` mode, or a display-p3 canvas (one pixel is enough). A
  canvas drawn from a worker never switches it. Source 3 saw the same
  switch with display-p3 canvases in Edge 153.
- There is no tone-mapping call for WebGL without flags
  (`drawingBufferToneMapping` and the `rec2100-pq` colour space appear
  with `--enable-experimental-web-platform-features`), and none is
  needed.
- Values above the display's peak (465 nits) reach the compositor as
  written; the display clips them. The page cannot learn the peak or the
  SDR white level: `screen.highDynamicRangeHeadroom` only exists behind a
  flag. `matchMedia('(dynamic-range: high)')` was true;
  `(video-dynamic-range: high)` was false.
- 2D canvases (`float16` included) and CSS colours stay at SDR.

### Decoded video: what the browser does to it

The bars picture, signalled as HDR (BT.2020 PQ), decoded with WebCodecs
(`optimizeForLatency`); 100 / 203 / 400 / 1000 / 4000 nits went in. The
page was in HDR (it held WebGPU `extended` canvases):

| way onto the page | hardware decoder (HEVC) | software decoder (AV1) |
|---|---|---|
| `<video>` fed with the frames (`MediaStreamTrackGenerator`) | 71 / 145 / 244 / 325 / 463 | 83 / 170 / 307 / 465 / 465 |
| 2D canvas `drawImage` | 68 / 139 / 175 / 210 / 280 | 68 / 139 / 207 / 277 / 280 |
| WebGL `texImage2D` (what the client does) | 61 / 83 / 107 / 147 / 221 | 134 / 280 / 280 / 280 / 280 |
| WebGPU `importExternalTexture` | 141 / 162 / 182 / 210 / 252 | 123 / 143 / 154 / 162 / 162 |

- Only `<video>` shows HDR. The browser maps it to the display its own
  way: with the stream's HDR10 metadata (4000-nit mastering) a 203-nit
  white came out at 145 nits, without metadata (the AV1 stream) at 170;
  the page's own white is 280.
- Every other way squeezes the picture into SDR, each with a different
  curve. The first two rows follow the stream's metadata, the last two
  the decoder: hardware AV1 gave the AV1 column in the first two rows and
  the HEVC column in the last two. The WebGL hardware result is the PQ
  codes untouched, shown as if they were sRGB; the software one was
  converted and clipped at SDR white.
- So a stream signalled as HDR is not something to build on: what the page
  receives depends on the API, on the decoder and on the metadata.

The same samples signalled as ordinary SDR (sRGB / BT.709), with the PQ
curve applied by our own shader (relative to a 203-nit white) on an HDR
canvas; 138 / 280 / 552 / 1379 / 5517 is the right answer:

| | on screen |
|---|---|
| WebGL float canvas, hardware HEVC | 133 / 275 / 537 / 1323 / 5369 |
| WebGPU `extended` canvas, hardware HEVC | 133 / 275 / 537 / 1329 / 5368 |
| WebGPU `extended` canvas, software AV1 | 135 / 279 / 543 / 1342 / 5284 |

- This works everywhere it was tried and gives the brightness we ask for,
  2-4 % low: the browser returns the top code as 253 of 255 (254 with the
  software decoder). A calibration, or a transfer that the browser passes
  exactly, has to be found when implementing.
- A hardware frame cannot be copied out as planes
  (`VideoFrame.format` is null); a software AV1 frame can (`I420P10`,
  1 ms for 720p).
- Edge decoded HEVC Main 10 in hardware, and AV1 10-bit in hardware and
  in software.

### Precision

A ramp with all 877 luma codes of a 10-bit picture went in; distinct
levels that came back:

| stream signalled as | WebGL `texImage2D`, any texture format, float included | WebGPU `importExternalTexture` |
|---|---|---|
| sRGB / BT.709, hardware | 254 | 254 |
| sRGB / BT.709, software | 255 | 255 |
| BT.2020 PQ, hardware | 256 | 533 |
| BT.2020 PQ, software | 126 | 149 |
| BT.2020 HLG, hardware | 256 | 533 |
| BT.2020 with an SDR transfer, hardware | 256 | 550 |
| BT.2020 with an SDR transfer, software | 255 | 255 |

- Through WebGL a decoded picture has 8 bits, whatever was sent.
- Through WebGPU it has more than 8 only for hardware frames signalled as
  HDR or wide gamut, which are the ones the browser alters (previous
  section). The wide-gamut row may be usable; whether its values pass
  unchanged was not checked.
- The PQ curve in 8 bits is coarse: between the 100 and 203-nit bars one
  code is a 3.8 % step in brightness (computed), against about 1 % for
  8-bit sRGB near white. Hence open question 2.
- Pixel data we upload ourselves is not affected: the 10-bit tiles above
  arrived exactly.

### What it means

- HDR on a WebGL canvas: yes, with a float drawing buffer, a canvas that
  is not opaque, and the small canvas on the page that switches it on.
- Lossless HDR tiles: yes, exactly, as 10-bit textures.
- HDR video: yes, signalled as SDR with our own curve, at 8 bits; or in a
  `<video>` element at full precision with the browser's brightness.
- Only Edge 156 on Windows was tested. By the user's decision the rest is
  assumed to behave the same.

## What would have to be done

A work list for whoever picks this up, not an agreed design.

Sunshine (task 003) does both halves and is a reference for the server
side: it asks duplication for 16-bit float first, has one set of shaders
for PQ output and another for linear to sRGB, sends HDR only when the
client asks and the display is in HDR, and needs 10-bit HEVC or AV1 for
it (`src/platform/windows/display_vram.cpp:~2025-2046`,
`src/platform/windows/display_base.cpp:~772-840`,
`src/video_colorspace.cpp:49-105` in `.tools/ref/Sunshine`). It avoids
the 10-bit integer capture format because it "seems to actually just
clamp" the float values.

### Server, both halves

1. **HDR state of the display.** Whether it is on, the SDR white level
   and the peak (`DisplayConfigGetDeviceInfo`, `IDXGIOutput6::GetDesc1`;
   the test tool reads all three). Followed while streaming: a switch of
   HDR reopens the capture, as a mode change does; a new white level only
   changes a shader constant (see the decision above).
2. **Capture in float.** Ask duplication for
   `DXGI_FORMAT_R16G16B16A16_FLOAT` first, BGRA as today when the display
   is not in HDR. The capture texture and the copies of changed regions
   become 16-bit float (8 bytes per pixel on the GPU). The first frame
   after starting can be empty (`LastPresentTime` 0): skip it.
3. **A conversion pass on the GPU**, right after capture, on
   `capture / k`. It replaces what Windows does today and has one or two
   outputs, below.
4. **Tile comparison.** Run it on one of the converted images, not on the
   float one, so that the CPU path keeps reading 4 bytes per pixel. The
   conversion must give the same output for the same input every frame
   (no changing dither), or every tile would count as changed.
5. **Cursor.** Its shape comes from duplication as SDR and is drawn by the
   client: no change expected. To check on an HDR desktop.
6. **Behind the platform traits.** The capture session says per frame
   whether the picture is HDR, with white level and peak; the conversion
   pass belongs to the platform (D3D11 here). Core, protocol and client
   know nothing of Windows, so that a Linux capture can provide the same
   later.

### SDR of our own (no client change)

7. The conversion pass writes the 8-bit BGRA image the rest of the
   pipeline already uses, as decided above: sRGB up to white, highlights
   rolled off keeping the hue, colours outside sRGB brought in, dither
   with a fixed pattern.
8. Nothing else changes: tiles, video and client stay as they are. This
   half can be done and judged alone, and by itself it turns a washed-out
   picture into the right one for everything that is not HDR content.

### HDR to the client

9. **A second output of the conversion pass**: the picture in multiples
   of white, in a transfer of our choice, 10 bits.
10. **Lossless tiles in 10 bits** (`R10G10B10A2`, 4 bytes per pixel as
    today): the shared screen copy, LZ4 / zstd and the client upload take
    them as they take BGRX now; they compress somewhat worse. The client
    uploads them as `RGB10_A2` textures.
11. **Video.** Per open question 2: 8 bits with our curve, signalled as
    SDR so that the browser leaves the samples alone; or 10-bit HEVC /
    AV1 signalled as PQ for a `<video>` element. H.264 can only carry the
    first. The encoder input becomes a second texture (the HDR output),
    in 10 bits for the second variant (`P010`; NVENC HEVC Main 10 and AV1
    take it, AMF and QuickSync unverified, x264 no).
12. **Protocol.** HELLO says that the picture is HDR, the transfer in use
    and the host's peak in multiples of white; the client says whether it
    can show HDR (with its display check, which can change when the
    window moves to another screen). A switch of HDR on the host is a new
    HELLO, like a display change.
13. **SDR and HDR clients on one display** (open question 5): both
    outputs kept side by side (twice the shared copy, compared once), or
    one picture for all and HDR only when every client can show it.

### Client

14. **Detect**: `matchMedia('(dynamic-range: high)')`, the float drawing
    buffer (`EXT_color_buffer_float` and `drawingBufferStorage`), the
    switch canvas (WebGPU, else display-p3), and for the `<video>` variant
    the 10-bit decoder. Anything missing: SDR as today.
15. **Canvas**: float drawing buffer, `alpha: true` (opaque is refused),
    output sRGB-encoded with 1.0 = SDR white; and on the page a 1-pixel
    visible canvas that keeps the page in HDR (open question 4).
16. **Shader**: both layers decoded from our transfer to linear, then
    encoded for the canvas. The lossless layer becomes a 10-bit texture;
    screen moves (the scratch copy) follow its format.
17. **Video frames**: `texImage2D` as today for the 8-bit variant; a
    `<video>` element fed with the decoder's frames for the other.
18. The stats overlay says whether the picture is HDR and why not.

### Order that keeps each step useful

1. Capture in float and the SDR conversion of our own (items 1-8): the
   right SDR picture for everybody, and the float capture the rest needs.
2. Client HDR canvas and 10-bit lossless tiles (10, 12, 14-16): a still
   desktop in HDR.
3. HDR video (11, 17) once open question 2 is decided.

## Linux

Best effort, as the user asked. What was found (sources 4 and 5):

- **X11 has no HDR** and X.org has no plans for it. Everything remothing
  captures on Linux is X11: real X displays and Xvfb. So there is no HDR
  picture to capture today, and an SDR picture needs no conversion.
- **HDR on Linux exists only under Wayland**: KDE Plasma 6, GNOME,
  Hyprland, sway, gamescope and others. remothing does not capture
  Wayland at all (task 003, candidate 11).
- **Capturing it**: screen sharing through the portal and PipeWire is not
  an HDR path (the ArchWiki lists it as broken with HDR10 on; a KWin
  request about HDR for screencast outputs is from July 2026).
  Sunshine captures HDR on Linux only by reading the display's
  framebuffer from the kernel (KMS, needs `CAP_SYS_ADMIN`), under
  gamescope or Plasma 6, with VAAPI 10-bit encoding, and calls it
  experimental.

Decision:

- Linux hosts: nothing to implement now. A display we capture is SDR and
  stays as it is.
- The work list keeps HDR state and conversion behind the platform traits
  (item 6), so a Wayland or KMS capture, if it is ever added, plugs into
  the same core, protocol and client.
- For that day: a framebuffer read through KMS on an HDR output is 10-bit
  PQ (BT.2020) with the connector's `HDR_OUTPUT_METADATA`; the conversion
  would decode it instead of dividing scRGB. The SDR white level is the
  compositor's own setting and not in KMS: start from 203 nits with a
  setting to change it. None of this was tried.
- Linux clients: HDR in browsers under Wayland is recent (Chromium from
  141, Firefox behind a preference). The client's detection decides; where
  it fails the picture is SDR, as today.

## Testing

- Needs a display in HDR mode. This PC's main display is in HDR; the one
  the demo streams is not. Switching HDR on a display, or moving the SDR
  brightness slider, changes what the user sees: ask first (`AGENTS.md`).
- The method of the browser test can check the finished feature without
  anybody looking: stream an HDR desktop to a client window on the HDR
  display and read both with the float capture; they should agree. For
  the SDR half: the greys of `levels.html` must arrive as themselves
  (32, 64, ... 255) at any slider position.
- Other browsers and devices, when somebody wants to check the
  assumption: open
  `.tools/hdr-probe/web/single.html?where=worker&hint=gpu` there (HTTPS
  or localhost; it is the setup recommended in open question 4). Without
  the capture tool the check is by eye: the right band must be clearly
  brighter than the left one.

## Not verified

- Any browser other than Edge 156 on Windows (assumed equal by decision).
- The SDR brightness slider at any position other than 280 nits on this
  PC: the dependence comes from the documentation, one measurement here
  and source 3. Whether Windows tells a program when it moves.
- How long a page stays in HDR, and whether the 1-pixel canvas has side
  effects (tried for a few seconds).
- Why a worker's canvas with `desynchronized` shows raw scRGB unless the
  WebGPU canvas is there, and whether today's opaque canvas behaves
  normally on an HDR display in real use.
- The cost of a float drawing buffer and of `alpha: true` for the client's
  latency (the opaque, desynchronized canvas was chosen for it).
- Latency of the `<video>` path.
- Whether the browser passes a wide-gamut SDR stream's values unchanged
  (the one case with more than 8 bits that is not tone-mapped).
- Banding of 8-bit HDR video in practice: the 3.8 % step is computed, no
  picture was judged.
- That NVENC, AMF and QuickSync through FFmpeg accept 10-bit input from a
  D3D11 texture.
- Everything in "Linux": read, not tried.
